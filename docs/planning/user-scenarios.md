## 1. 사용자 페르소나

### 페르소나 1: 창업 기획자 (김지원, 32세)

| 항목 | 내용 |
|------|------|
| **직업** | 스타트업 기획자 / 비개발 직군 |
| **기술 수준** | HTML/CSS 기초 이해, 코딩 경험 없음 |
| **목표** | 아이디어를 빠르게 MVP로 만들어 시장 검증 |
| **불만** | 외주 비용이 비싸고, 프롬프트만으로는 원하는 결과가 안 나옴 |
| **YHAI 기대** | 전문가와 대화하며 요구사항을 구체화하고, 코딩 없이 완성도 높은 앱 생성 |
| **핵심 니즈** | 가이디드 대화, 쉬운 수정, 빠른 배포 |

### 페르소나 2: 1인 개발자 (박서준, 28세)

| 항목 | 내용 |
|------|------|
| **직업** | 프리랜서 풀스택 개발자 |
| **기술 수준** | React, Node.js 숙련, 아키텍처 설계 경험 |
| **목표** | 반복적인 보일러플레이트를 AI에게 맡기고, 핵심 로직에 집중 |
| **불만** | 기존 AI 빌더는 복잡한 요구사항을 제대로 이해 못 함 |
| **YHAI 기대** | 도메인 전문가의 조언으로 놓치기 쉬운 설계 포인트 보완 |
| **핵심 니즈** | 코드 품질, 아키텍처 투명성, 세밀한 수정 컨트롤 |

### 페르소나 3: 소상공인 (이미나, 45세)

| 항목 | 내용 |
|------|------|
| **직업** | 오프라인 카페 사장, 온라인 진출 희망 |
| **기술 수준** | 스마트폰 기본 사용, IT 용어에 익숙하지 않음 |
| **목표** | 카페 예약/주문 웹사이트 구축 |
| **불만** | 기술 용어를 모르니 무엇을 요청해야 할지도 모름 |
| **YHAI 기대** | 전문가가 먼저 필요한 것을 질문해주고, 쉬운 말로 안내 |
| **핵심 니즈** | 능동적 AI, 쉬운 언어, 시각적 미리보기 |

## 2. 핵심 사용자 시나리오

### 시나리오 1: 첫 프로젝트 -- 온보딩에서 전문가 대화까지

**페르소나**: 김지원 (창업 기획자)
**목표**: "반려동물 용품 구독 서비스"를 위한 웹앱 MVP 제작

#### 사용자 플로우

```
[랜딩 페이지]
    |
    v
[회원가입] -- 소셜 로그인 (Google/GitHub/Kakao)
    |
    v
[온보딩 -- 인텐트 캡처]
    |  "어떤 것을 만들고 싶으세요?"
    |  --> "반려동물 용품 구독 서비스요"
    |
    v
[유사 사례 카드 제시]
    |  AI가 유사 서비스 3-5개 카드로 표시
    |  --> "바크박스와 비슷한 건가요?" (원클릭 선택)
    |  --> 초기 컨텍스트 강화
    |
    v
[전문가 자동 추천]
    |  "이 프로젝트에 다음 전문가를 추천합니다:"
    |  [v] 이커머스/구독 전문가 -- 구독 모델, 결제, 재고 관리
    |  [v] UI/UX 전문가 -- 사용성, 구독 흐름 설계
    |  [ ] 마케팅 전문가 -- 랜딩페이지, 전환율 (선택사항)
    |
    v
[가이디드 대화 시작]
    |
    |  구독 전문가: "안녕하세요! 반려동물 구독 서비스를 만드시려는군요.
    |     몇 가지 질문으로 시작할게요:
    |     1. 타겟 반려동물 종류는? (강아지/고양이/전체)
    |     2. 구독 주기는? (주간/격주/월간)
    |     3. 커스터마이징이 가능한가요? (사이즈/알레르기 필터)"
    |
    |  --> 사용자가 답변 (예시 칩 선택 또는 자유 입력)
    |
    |  UI/UX 전문가: "구독 서비스에서 중요한 화면들을 정리해볼게요:
    |     - 상품 브라우징
    |     - 구독 플랜 선택
    |     - 박스 커스터마이징
    |     - 배송 추적
    |     이 중 가장 중요한 화면은 뭘까요?"
    |
    v
[진행률 표시] "요구사항 정의 40% 완료"
    |
    v
[대화 계속...] (시나리오 2로 이어질 수 있음)
```

#### 핵심 UI 요소
- **대화 영역**: 메인 채팅, 전문가별 아바타/이름/색상 구분
- **사이드 패널**: 참여 전문가 목록, "+" 버튼으로 추가 가능
- **진행률 바**: 요구사항 정의 완성도 표시
- **예시 칩**: 각 질문에 원클릭 답변 옵션 제공

### 시나리오 2: 전문가 추가 초빙 -- 대화 중 전문 영역 확장

**페르소나**: 김지원 (이어서)
**상황**: 구독 서비스 대화 중 결제에 대한 심층 논의가 필요해진 경우

#### 사용자 플로우

```
[대화 진행 중]
    |
    |  사용자: "결제는 카카오페이랑 카드 결제 둘 다 되면 좋겠어요"
    |
    v
[자동 감지 -- 결제 도메인 트리거]
    |
    v
[추천 카드 삽입 (대화 흐름 내)]
    |  "결제 시스템에 대해 더 깊은 논의가 필요해 보입니다.
    |     결제/핀테크 전문가를 초대할까요?"
    |     [초대하기] [나중에]
    |
    v (사용자 "초대하기" 클릭)
    |
[전문가 합류]
    |
    |  결제 전문가: "안녕하세요! 지금까지 대화를 검토했습니다.
    |     구독 결제에 대해 3가지 방식을 제안드릴게요:
    |     1. PG 직접 연동 (토스페이먼츠/NHN KCP)
    |     2. 구독 결제 전문 플랫폼 (Bootpay 정기결제)
    |     3. 카카오페이 구독 결제 API
    |     각각의 장단점을 설명드릴까요?"
    |
    v
[멀티 전문가 크로스 레퍼런스]
    |
    |  구독 전문가: "결제 전문가가 제안한 2번 방식이면,
    |     앞서 논의한 구독 플랜 변경/일시정지 기능도 쉽게 구현 가능합니다."
    |
    v
[요구사항 자동 업데이트]
    |  새로운 요구사항 카드가 자동 추가됨:
    |  - "PG 결제 연동 (카드 + 카카오페이)" -- 결제 전문가 제안
    |  - "정기결제 관리 (변경/일시정지/취소)" -- 구독 전문가 보완
```

#### 전문가 수동 초빙 (대안 흐름)
```
사용자가 사이드 패널의 "+" 버튼 클릭
    |
    v
[전문가 갤러리]
    |  현재 대화 컨텍스트 기반 추천순 정렬
    |  +----------------------------------+
    |  | 추천 (현재 대화와 연관도 높음)       |
    |  | 결제/핀테크 전문가                  |
    |  |    결제 흐름, PG 연동, 구독 결제    |
    |  |                                  |
    |  | 물류/배송 전문가                    |
    |  |    배송 추적, 재고 관리, 풀필먼트    |
    |  |                                  |
    |  | 기타 전문가                        |
    |  | 마케팅 전문가                      |
    |  | 커뮤니티 전문가                    |
    |  | ...                              |
    |  +----------------------------------+
    |
    v
카드 클릭 --> 전문가 소개 팝오버 --> "초대하기" --> 전문가 합류
```

#### 전문가 퇴장 흐름
```
사이드 패널에서 전문가 카드의 "x" 클릭
    |
    v
확인 다이얼로그: "결제 전문가를 퇴장시킬까요? 기여 내용은 유지됩니다."
    |
    v (확인)
    |
전문가 퇴장 -- 대화에서 비활성화 (기여 기록 보존)
나중에 동일 전문가 재초빙 가능 (이전 기여 기억)
```

### 시나리오 3: 요구사항 확정 --> PM Agent의 AI 팀 동적 생성 --> 단계적 빌드

**페르소나**: 김지원 (이어서)
**상황**: 전문가 대화 완료, 요구사항을 확정하고 빌드를 시작하는 단계

> **v2 전면 재설계**: 고정 5인 팀이 아닌, PM Agent가 요구사항을 분석하여 프로젝트별 맞춤 팀을 동적 생성하고, Phase별 단계적 구현을 실행한다. Git Worktree 격리와 메시지박스 기반 협업을 적용한다.

#### 핵심 차별점 (v1 대비 변경)

| 영역 | v1 | v2 |
|------|----|----|
| 팀 구성 | 고정 5명 (항상 동일) | PM Agent가 프로젝트별 동적 N명 구성 |
| 팀 생성 과정 | "팀을 구성하고 있습니다..." 한 줄 | PM의 분석 과정을 사용자에게 투명하게 스트리밍 |
| 실행 방식 | 모든 에이전트 동시 시작 | Phase 분해 후 의존성 기반 순차/병렬 실행 |
| 파일 충돌 대책 | 미정의 | Git Worktree 격리 + 3-way 머지 + 사용자 폴백 |
| 에이전트 간 통신 | 미정의 | 메시지박스 기반 직접 통신 (API 인터페이스 합의 등) |
| 사용자 개입 | 빌드 시작 버튼만 | 팀 구성 승인, Phase 계획 승인, 빌드 중 코파일럿 개입 |
| 비용 관리 | 미정의 | 사전 비용 예측 + 실시간 비용 대시보드 + 예산 게이트 |

#### 내부 아키텍처: Git Worktree 격리 + 메시지박스 협업

```
+------------------------------------------------------------------+
|                        PM Agent (팀 리드)                          |
|   - 공유 태스크 리스트 관리 (pending / in_progress / completed)     |
|   - Phase 전환 판단                                               |
|   - 충돌 감지 시 사용자 알림                                       |
+------------------------------------------------------------------+
        |                    |                    |
        v                    v                    v
+----------------+  +----------------+  +----------------+
| Frontend Agent |  | Backend Agent  |  | QA Agent       |
| worktree-fe/   |  | worktree-be/   |  | worktree-qa/   |
| (독립 HEAD)     |  | (독립 HEAD)     |  | (독립 HEAD)     |
+----------------+  +----------------+  +----------------+
        |                    |
        |   [메시지박스]       |
        |<--- "GET /api/subscriptions 응답 스키마:"
        |     { id, planName, price, interval }
        |---> "확인. SubscriptionCard에서 사용합니다."
        |                    |

각 에이전트 완료 시:
  worktree-fe/ --> git commit --> merge to main
  worktree-be/ --> git commit --> merge to main
  충돌 발생 시 --> PM Agent가 자동 해결 시도
                   실패 시 --> 사용자에게 선택지 제시
```

**Git Worktree 격리 원칙** (업계 표준 -- Cursor 2.0, VS Code 1.107 채택):
- 에이전트마다 독립 워킹 트리를 부여하여 편집 충돌을 구조적으로 차단
- `.git/` 디렉토리는 공유하므로 커밋과 브랜치 정보는 실시간 동기화
- 파일 쓰기 전 다른 워크트리와의 충돌 사전 체크

**메시지박스 협업** (Claude Agent Teams 패턴):
- 팀메이트 간 직접 통신으로 팀 리드 병목 제거
- API 인터페이스, 데이터 타입 등의 합의를 에이전트끼리 직접 수행
- PM Agent는 중재만 담당 (Hub-and-Spoke가 아닌 Mesh 구조)

## 6. AI 팀 빌드 메커니즘 상세

> PM Agent가 Claude Code의 팀장 역할을 수행하여, 필요한 에이전트를 자동 생성하고, 단계적으로 구현을 실행하는 메커니즘.

### 6.1 PM Agent의 팀 구성 프로세스

PM Agent는 요구사항 문서를 입력받아 다음 3단계를 순차 실행한다.

```
[입력: 확정된 요구사항 문서]
       |
       v
+------------------------------------------+
| 1단계: 도메인 분석                          |
|   - 요구사항에서 기술 도메인 추출             |
|   - 필요 기술 스택 결정                     |
|   - 외부 서비스 연동 필요 여부 판단           |
|                                          |
|   예: "구독 결제 + 배송 추적 + 회원 관리"     |
|   --> Next.js, FastAPI, Prisma, Bootpay    |
+------------------------------------------+
       |
       v
+------------------------------------------+
| 2단계: 역할 판단                            |
|   - 도메인 복잡도에 따른 필요 역할 도출       |
|   - 역할별 담당 범위 정의                    |
|   - 불필요한 역할 배제 근거 설명              |
|                                          |
|   간단한 랜딩 --> Frontend 1명             |
|   SaaS MVP   --> FE + BE + DB 3명         |
|   복잡한 SaaS --> FE + BE + DB + QA + DevOps 5~6명 |
+------------------------------------------+
       |
       v
+------------------------------------------+
| 3단계: 에이전트 생성                         |
|   - 각 역할에 대한 시스템 프롬프트 동적 생성   |
|   - 프로젝트 컨텍스트(요구사항, 기술 스택,     |
|     코딩 컨벤션) 주입                        |
|   - Git Worktree 할당                      |
|   - 공유 태스크 리스트에 태스크 등록           |
+------------------------------------------+
```

### 6.2 단계적 구현 흐름 (Phase 실행)

PM Agent가 태스크를 Phase로 분해하는 기준:

| 기준 | 설명 | 예시 |
|------|------|------|
| **의존성 우선** | 하위 작업이 상위 결과에 의존 | DB 스키마 --> API --> UI 순 |
| **병렬 가능성** | 독립적인 작업은 같은 Phase | FE와 BE가 서로 다른 기능 구현 |
| **충돌 위험** | 동일 파일 수정 가능성이 높으면 순차 | 결제 BE --> 결제 FE 순차 |
| **검증 시점** | 통합 테스트가 필요한 시점에 Phase 경계 | QA는 항상 마지막 Phase |

**Phase 전환 프로토콜**:

```
Phase N 실행 중
       |
       v
모든 에이전트 태스크 completed?
       |
       +-- 아니오 --> 대기 (미완료 에이전트 독촉)
       |
       +-- 예
            |
            v
       각 worktree의 변경사항 머지
            |
            +-- 머지 성공 --> Phase N+1 에이전트에
            |                이전 Phase 결과물 주입
            |
            +-- 머지 충돌 --> PM Agent 자동 해결 시도
                              |
                              +-- 성공 --> Phase N+1 진행
                              +-- 실패 --> 사용자에게 선택지 제시
```

### 6.3 에이전트 간 협업 패턴

**패턴 1: API 인터페이스 합의 (가장 빈번)**
```
Backend Agent --> 메시지박스 --> Frontend Agent
  "GET /api/products 응답 스키마:
   { id: string, name: string, price: number,
     thumbnailUrl: string, category: string }"

Frontend Agent --> 메시지박스 --> Backend Agent
  "확인. ProductCard 컴포넌트에서 사용합니다.
   추가 요청: 재고 수량(stock) 필드도 포함해주세요."

Backend Agent --> 메시지박스 --> Frontend Agent
  "stock: number 필드 추가했습니다."
```

**패턴 2: 공유 타입 정의 (Type-First Development)**
```
DB 설계자가 Phase 1에서 생성한 Prisma 스키마:
  model Subscription {
    id        String   @id @default(cuid())
    status    SubscriptionStatus  // ENUM
    planId    String
    userId    String
    ...
  }

PM Agent가 이를 공유 타입으로 변환하여 모든 에이전트에 배포:
  // packages/shared/types/subscription.ts
  export type SubscriptionStatus = 'active' | 'paused' | 'cancelled'
  export interface Subscription { id: string; status: SubscriptionStatus; ... }

Frontend/Backend 에이전트 모두 동일 타입을 import하여 사용
```

**패턴 3: 문제 에스컬레이션**
```
Frontend Agent --> PM Agent
  "결제 완료 후 리다이렉트 URL을 결정할 수 없습니다.
   Backend의 결제 콜백 엔드포인트가 아직 구현되지 않았습니다."

PM Agent --> Backend Agent
  "결제 콜백 엔드포인트(POST /api/payments/callback)를
   우선 구현해주세요. Frontend가 대기 중입니다."

PM Agent --> Frontend Agent
  "Backend에 우선 구현을 요청했습니다. 다른 태스크를
   먼저 진행하고, 콜백 URL은 placeholder로 처리해주세요."
```

## 7. 알려진 문제점과 해결 전략

> 멀티 에이전트 오케스트레이션의 6대 문제와 YHAI의 구조적 해결 메커니즘.
> 근거: Claude Agent Teams, Cursor 2.0, Devin, LangGraph, MIT NANDA 조사 등 실제 사례 기반.

### 7.1 파일 충돌 (File Conflict)

**문제**: 멀티 에이전트가 동일 저장소에서 동시 작업 시, 같은 파일을 서로 다른 방향으로 수정하여 코드가 깨진다.

**실제 사례**: 업계에서 Cursor 2.0(2025.10), VS Code 1.107이 Git Worktree를 표준 해법으로 채택.

**발생 시나리오**: Frontend Agent가 `src/types/api.ts`에 `ProductResponse` 타입을 정의하는 동시에, Backend Agent가 같은 파일에 `OrderResponse` 타입을 추가. 두 에이전트 모두 파일 끝에 내용을 추가하여 머지 시 한쪽 변경이 유실.

**YHAI 해결 메커니즘**:

```
[1. 사전 예방] Git Worktree 격리
  - 각 에이전트에 독립 워크트리 부여
  - worktree-fe/, worktree-be/ 각각 독립된 HEAD와 index
  - 작업 중 다른 에이전트의 파일과 물리적으로 분리

[2. 충돌 감지] 머지 전 사전 체크
  - PM Agent가 각 에이전트의 변경 파일 목록을 실시간 추적
  - 동일 파일 수정 감지 시 경고

[3. 자동 해결] 3-way 머지 시도
  - git merge --no-commit 으로 자동 머지 시도
  - 충돌 없음 --> 자동 커밋
  - 충돌 발생 --> PM Agent가 충돌 내용 분석 후 자동 해결 시도

[4. 사용자 선택] 자동 해결 실패 시
  +--------------------------------------------------+
  | 파일 충돌 발생: src/types/api.ts                    |
  |                                                    |
  | Frontend 버전:                Backend 버전:         |
  | export type ProductResponse   export type OrderRes  |
  | = { id, name, price }        = { id, total }       |
  |                                                    |
  | [두 변경 모두 유지] [Frontend 우선] [Backend 우선]    |
  +--------------------------------------------------+
```

### 7.2 컨텍스트 유실 (Context Loss)

**문제**: 에이전트가 독립 컨텍스트 창에서 실행되므로, 다른 에이전트의 결정사항을 모른 채 작업하여 일관성이 깨진다.

**근거**: MIT NANDA 조사(2025) -- AI 파일럿의 95%가 측정 가능한 비즈니스 임팩트를 내지 못하는 핵심 원인이 "에이전트를 고립된 도구로 설계한 것".

**YHAI 해결 메커니즘**:

```
[공유 태스크 리스트] -- 중앙 단일 진실 공급원
  - 모든 에이전트가 읽고 쓸 수 있는 태스크 큐
  - 각 태스크에 결과물(아티팩트) 첨부
  - 예: "DB 스키마 완료" 태스크에 Prisma 모델 파일 경로 첨부

[메시지박스 기반 합의]
  - 에이전트 간 인터페이스 결정 시 직접 통신
  - API 응답 스키마, 데이터 타입 등을 합의

[Phase 경계 동기화]
  - Phase 1(DB) 완료 --> 결과물을 Phase 2 에이전트에 주입
  - 에이전트가 이전 Phase 결과를 참조하고 시작
  - 컨텍스트 단절을 구조적으로 방지
```

### 7.3 에러 전파 (Error Propagation)

**문제**: 한 에이전트의 잘못된 출력이 다음 에이전트의 입력이 되어, 파이프라인 전체에 걸쳐 잘못된 결과를 생산한다.

**근거**: CrewAI에서 소수점 직렬화 버그(68.81% --> 0.6878)가 에이전트 체인 전체에 전파된 사례. LangGraph의 철학 -- "실패는 명시적이고 통제된 방식으로 처리되어야 한다."

**YHAI 해결 메커니즘**:

```
[체크포인트 시스템]
  - 매 Phase 완료 시 전체 상태 스냅샷 저장 (Git 커밋 기반)
  - Phase 2에서 문제 발견 시 Phase 1부터 재실행 가능
  - 재실행 범위를 문제 발생 Phase로 한정

[QA 에이전트 검증 게이트]
  - Phase 4에서 QA 에이전트가 통합 테스트 실행
  - 타입 불일치, 데이터 변환 오류 등을 자동 감지
  - 실패 시 해당 에이전트에게 수정 지시 + 재테스트

[롤백 메커니즘]
  - 사용자가 "이전 Phase로 돌아가기" 선택 가능
  - Git 커밋 히스토리 기반으로 특정 Phase 시점으로 복원
```

### 7.4 무한 루프 (Infinite Loop)

**문제**: 에이전트가 종료 조건을 인식하지 못하고 동일한 작업을 반복하거나, 에러 수정 시도가 새로운 에러를 만들어 무한히 순환한다.

**근거**: GPT-4 기준 2시간 루프가 $15~40 비용 발생. "Loop Drift" -- 에이전트가 종료 신호를 잘못 해석하거나 내부 상태 불일치로 무한 실행.

**YHAI 해결 메커니즘**:

```
[가드레일 1: max_steps 캡]
  - 에이전트당 최대 실행 스텝 수 설정 (기본: 30 steps)
  - 상한 도달 시 에이전트 자동 중단 + PM Agent에 보고

[가드레일 2: 반복 출력 감지]
  - 에이전트의 최근 N개 출력 비교
  - 동일/유사 출력 3회 이상 반복 시 Loop Drift 판정
  - 즉시 중단 + 사용자 알림:
    "Frontend Agent가 같은 파일을 반복 수정하고 있습니다.
     [에이전트 재시작] [직접 수정 지시] [이 작업 건너뛰기]"

[가드레일 3: 시맨틱 완료 체크]
  - PM Agent가 각 태스크의 완료 조건을 사전 정의
  - 예: "SubscriptionPlanPage 컴포넌트가 존재하고,
    props로 plans 배열을 받고, 가격을 표시한다"
  - 조건 미충족 시 구체적 피드백과 함께 재시도 (최대 3회)
```

### 7.5 비용 폭발 (Cost Explosion)

**문제**: 멀티 에이전트 병렬 실행 시 비용이 기하급수적으로 증가. 무한 루프나 과도한 디버깅 시 예측 불가능한 비용 발생.

**근거**: 3-팀 구성 시 토큰 비용 약 3~4배 증가(Claude Agent Teams 공식 데이터). 악의적 재귀 공격(Agentic Resource Exhaustion)은 수 분 내 수천 달러 소진 가능.

**YHAI 해결 메커니즘**:

```
[빌드 전 비용 예측]
  - Phase 실행 계획 단계에서 예상 비용 사전 표시
  - "총 예상 비용: ~$2.50 (Phase 4개, 에이전트 4명)"
  - 사용자가 비용을 확인하고 빌드 시작 결정

[실시간 비용 대시보드]
  - Mission Control에 현재 비용 실시간 표시
  - "현재 비용: $1.20 / 예산 $5.00"
  - 에이전트별 비용 분배:
    Frontend: $0.45 | Backend: $0.50 | DB: $0.15 | PM: $0.10

[토큰 예산 + 사용자 승인 게이트]
  - 프로젝트별 토큰 예산 사전 설정
  - 예산 70% 소진 시 경고, 90% 소진 시 자동 일시정지
  - 사용자에게 선택지 제시:
    [예산 추가] [현재 상태로 완료] [빌드 취소]
```

### 7.6 품질 불일치 (Quality Inconsistency)

**문제**: 각 에이전트가 독립적으로 코드를 생성하므로, 코딩 스타일, 네이밍 컨벤션, 에러 처리 방식이 에이전트마다 달라 전체 코드베이스의 일관성이 깨진다.

**근거**: Devin의 교훈 -- PR 머지율이 34%에서 67%로 개선된 핵심 요인 중 하나가 "일관된 코딩 스타일 적용".

**YHAI 해결 메커니즘**:

```
[공유 코딩 컨벤션 문서]
  - PM Agent가 빌드 시작 시 프로젝트 코딩 컨벤션 생성
  - 모든 에이전트의 시스템 프롬프트에 포함:
    - 네이밍: camelCase (변수/함수), PascalCase (컴포넌트/타입)
    - 에러 처리: 모든 API 호출에 try-catch + 사용자 친화적 에러 메시지
    - 파일 구조: feature-based 폴더 구조
    - 임포트 순서: 외부 라이브러리 > 내부 모듈 > 상대 경로

[PM Agent 코드 리뷰]
  - 각 에이전트의 커밋을 PM Agent가 자동 리뷰
  - 컨벤션 위반 감지 시 에이전트에게 수정 요청

[린트/포맷 자동 실행]
  - 모든 에이전트 커밋 전 ESLint + Prettier 자동 실행
  - 통과하지 못한 커밋은 거부
```

## 8. 창의적 차별화 아이디어

> 경쟁사(v0, Bolt, Lovable)에 없는 YHAI 고유 경험. 채택 가능한 7개 아이디어.

### 8.1 코파일럿 빌드 (Copilot Build) -- 우선순위: P1

빌드 진행 중 사용자가 실시간으로 개입하여 방향을 수정할 수 있다. 기존 AI 빌더는 "프롬프트 입력 --> 결과 대기"의 일방향 구조지만, YHAI에서는 빌드 중에도 사용자가 채팅으로 지시를 보낼 수 있다.

```
[Mission Control 하단 입력창]

사용자: "구독 플랜 페이지에 연간 할인 옵션도 추가해주세요"
  |
  v
PM Agent: "확인. Frontend Agent에 태스크를 추가합니다.
  현재 Phase 2 진행 중이므로 바로 반영됩니다."
  |
  v
Frontend Agent: 실행 중인 태스크에 연간 할인 옵션 추가
```

**사용자 가치**: 빌드 결과를 기다린 후 수정하는 것이 아니라, 진행 중에 방향을 조정하여 재빌드 비용 절감.
**구현 복잡도**: 중간 -- PM Agent의 태스크 큐에 실시간 추가 기능 필요.
**차별성**: v0, Bolt, Lovable 모두 "입력 --> 대기 --> 결과" 구조. 빌드 중 개입은 없음.

### 8.2 사고 과정 스트리밍 (Thinking Stream) -- 우선순위: P1

에이전트의 의사결정 과정을 사용자에게 투명하게 보여준다. 왜 이 라이브러리를 선택했는지, 왜 이 구조로 설계했는지, 어떤 대안을 고려했고 왜 기각했는지를 실시간으로 스트리밍한다.

```
[에이전트 사고 과정 패널] -- 접기/펼치기 가능

Backend Agent 사고 과정:
  "결제 연동 방식을 결정합니다..."

  고려한 옵션:
  1. 토스페이먼츠 직접 연동
     + 국내 점유율 1위, 문서 우수
     - 정기결제 설정이 복잡
  2. Bootpay 정기결제 API   <-- 선택
     + 구독 결제 전용 API, 설정 간단
     + 카카오페이 + 카드 결제 통합 지원
     - 수수료 약간 높음
  3. Stripe
     - 한국 원화 결제 제약

  결정: Bootpay 정기결제 API (요구사항의 카카오페이 + 카드 결제
  동시 지원 조건에 가장 부합)
```

**사용자 가치**: 블랙박스 불안감 해소. 개발자 사용자는 에이전트의 기술 결정을 학습할 수 있고, 비개발자도 왜 이렇게 만들어졌는지 이해 가능.
**구현 복잡도**: 낮음 -- Claude의 extended thinking 기능을 파싱하여 UI에 표시.
**차별성**: 모든 경쟁사가 블랙박스. 사고 과정을 보여주는 AI 빌더는 없음.

### 8.3 전문가 디베이트 (Expert Debate) -- 우선순위: P1

시나리오 1-2의 전문가 대화 단계에서, 전문가들이 서로 다른 의견을 가질 때 토론하는 과정을 사용자에게 보여준다. 사용자는 토론을 관찰하고 최종 결정을 내린다.

```
[전문가 디베이트 발생]

  SaaS 전문가: "구독 플랜은 3단계(Free/Pro/Enterprise)가
    업계 표준입니다. 전환율 최적화에 검증된 구조입니다."

  UX 전문가: "반대합니다. 반려동물 구독은 B2C 서비스이므로
    3단계 플랜은 복잡합니다. 단일 플랜 + 주기 선택이
    사용자 혼란을 줄입니다."

  SaaS 전문가: "단일 플랜은 업셀 기회를 놓칩니다.
    최소 2단계(Basic/Premium)를 권장합니다."

  UX 전문가: "그렇다면 2단계 + 주기 선택(월간/연간)으로
    타협하면 어떨까요?"

  +--------------------------------------------------+
  | 당신의 선택:                                       |
  | [A] 3단계 플랜 (Free/Pro/Enterprise)               |
  | [B] 2단계 + 주기 선택 (Basic/Premium x 월간/연간)    |
  | [C] 단일 플랜 + 주기 선택                           |
  | [D] 직접 입력                                      |
  +--------------------------------------------------+
```

**사용자 가치**: 전문가의 다양한 관점을 이해하고 정보에 기반한 결정을 내릴 수 있음. "AI 추천을 따르는 것"이 아닌 "사용자의 의사결정"이 됨.
**구현 복잡도**: 낮음 -- 전문가 페르소나 간 의견 충돌 시 토론 형식으로 출력하도록 프롬프트 설계.
**차별성**: 모든 경쟁사가 단일 관점 제시. 다중 관점 토론은 YHAI 고유 경험.

### 8.4 브랜치 빌드 (Branch Build) -- 우선순위: P2

빌드 중 여러 해결 방안이 있을 때, 에이전트가 Git 브랜치를 분기하여 각 방안을 별도로 구현한다. 사용자가 결과를 비교하고 원하는 브랜치를 선택한다.

```
Backend Agent: "인증 방식에 대해 2가지 접근이 가능합니다."

  +-- Branch A: JWT + httpOnly Cookie --------+
  | + 서버리스 친화적, 세션 서버 불필요          |
  | - 토큰 갱신 로직 필요                       |
  | [미리보기]                                 |
  +-------------------------------------------+

  +-- Branch B: Session 기반 인증 ---------------+
  | + 구현 단순, 즉시 만료 가능                    |
  | - Redis 세션 스토어 필요                      |
  | [미리보기]                                    |
  +----------------------------------------------+

  [Branch A 선택] [Branch B 선택]
```

**사용자 가치**: 기술 결정에서 사용자에게 선택권 부여. "AI가 결정한 것"이 아니라 "사용자가 선택한 것"이 되어 결과물에 대한 주인의식 증가.
**구현 복잡도**: 중간 -- Git 브랜치 분기 + 각 브랜치별 에이전트 실행 + 비교 UI.

### 8.5 A/B 빌드 (A/B Build) -- 우선순위: P2

동일한 요구사항을 서로 다른 디자인/아키텍처 접근으로 병렬 생성한다. 사용자가 두 결과물을 나란히 비교하고 선호하는 버전을 선택하거나 두 버전의 장점을 조합한다.

```
사용자: "랜딩 페이지를 두 가지 스타일로 만들어주세요"

  +-- Version A -----------------+  +-- Version B -----------------+
  | 미니멀 스타일                  |  | 임팩트 스타일                  |
  | 깔끔한 타이포그래피            |  | 대형 히어로 이미지              |
  | 여백 중심 레이아웃             |  | 동영상 배경                   |
  | 단색 CTA 버튼                 |  | 그라데이션 CTA 버튼            |
  |                              |  |                              |
  | 전환율 예상: 3.2%             |  | 전환율 예상: 4.1%             |
  | 로딩 속도: 1.2s               |  | 로딩 속도: 2.8s               |
  +------------------------------+  +------------------------------+

  [A 선택] [B 선택] [A의 레이아웃 + B의 CTA 버튼 조합]
```

**사용자 가치**: 디자인 결정에서 비교 선택이 가능. 비개발자에게 "보고 선택"하는 직관적 경험.
**구현 복잡도**: 높음 -- 동일 요구사항으로 2개의 독립 빌드 병렬 실행 + 비교 UI + 조합 기능.

### 8.6 빌드 리플레이 (Build Replay) -- 우선순위: P2

완성된 앱의 생성 과정을 타임랩스 영상처럼 재생할 수 있다. 빈 프로젝트에서 완성된 앱까지 코드가 추가되고 화면이 구성되는 과정을 가속 재생으로 보여준다.

```
[빌드 완료 후]

  "빌드 과정을 리플레이로 보시겠어요?"

  +--------------------------------------------------+
  | [빌드 리플레이]                        [x1] [x4]   |
  |                                                    |
  |  00:00  빈 프로젝트 생성                            |
  |  00:15  DB 스키마 정의 (6개 테이블)                  |
  |  00:30  Backend API 뼈대 생성                       |
  |  00:45  Frontend 레이아웃 + 라우팅                   |
  |  01:00  ProductCard 컴포넌트 구현                    |
  |  01:15  [지금 보는 중] SubscriptionPlan 페이지       |
  |  ...                                               |
  |  03:00  E2E 테스트 통과                             |
  |                                                    |
  |  좌측: 파일 트리 변화    우측: 라이브 프리뷰 변화       |
  |                                                    |
  |  [<<] [>] [>>]          타임라인 슬라이더             |
  +--------------------------------------------------+
```

**사용자 가치**: 교육적 가치(어떤 순서로 앱이 만들어지는지 학습), 공유 가치(SNS에 빌드 과정 공유 가능), 신뢰 구축(AI가 실제로 무엇을 했는지 확인).
**구현 복잡도**: 중간 -- Git 커밋 히스토리 + 각 커밋 시점의 프리뷰 스냅샷을 타임라인 UI로 재생.
**차별성**: 경쟁사에 이런 기능 전무. 바이럴 마케팅 소재로 활용 가능.

### 8.7 스냅샷 포크 (Snapshot Fork) -- 우선순위: P2

완성된 프로젝트를 다른 사용자가 "포크"하여 자신의 서비스로 커스터마이징할 수 있다. YHAI 사용자 커뮤니티에서 공개된 프로젝트를 탐색하고, 마음에 드는 프로젝트를 기반으로 시작한다.

```
[YHAI 갤러리]

  인기 프로젝트:
  +-------------------+  +-------------------+  +-------------------+
  | 펫박스 구독 서비스  |  | 카페 예약 시스템    |  | SaaS 대시보드      |
  | 구독 결제, 배송    |  | 예약, 메뉴 관리    |  | 분석, 팀 관리      |
  | 추적, 회원 관리    |  | POS 연동           |  | 결제, 대시보드      |
  | [포크하기]         |  | [포크하기]         |  | [포크하기]         |
  +-------------------+  +-------------------+  +-------------------+

  사용자가 "포크하기" 클릭:
    --> 프로젝트 복사 + 전문가 대화 시작
    --> "펫박스를 기반으로 어떤 부분을 바꾸고 싶으세요?"
    --> 사용자: "반려동물 대신 꽃 정기배송으로 바꾸고 싶어요"
    --> 전문가: 도메인 변경에 필요한 수정사항 분석 + 부분 재빌드
```

**사용자 가치**: 처음부터 만들 필요 없이 검증된 구조에서 시작. 온보딩 시간 대폭 단축. 커뮤니티 효과로 플랫폼 가치 증가.
**구현 복잡도**: 높음 -- 프로젝트 공유 시스템, 갤러리 UI, 포크 + 부분 재빌드 엔진.

### 8.8 창의적 아이디어 우선순위 매트릭스

| 아이디어 | 영향력 | 구현 복잡도 | 우선순위 | 비고 |
|---------|--------|-----------|---------|------|
| 사고 과정 스트리밍 | 높음 | 낮음 | **P1** | extended thinking 파싱만으로 구현. 차별화 효과 큼 |
| 코파일럿 빌드 | 높음 | 중간 | **P1** | 빌드 중 개입은 재빌드 비용 절감에 직결 |
| 전문가 디베이트 | 중간 | 낮음 | **P1** | 프롬프트 설계로 구현. 사용자 의사결정 경험 향상 |
| 브랜치 빌드 | 중간 | 중간 | **P2** | Git 분기 활용. A/B 빌드의 전 단계 |
| 빌드 리플레이 | 중간 | 중간 | **P2** | 바이럴 마케팅 효과. 브랜딩에 기여 |
| A/B 빌드 | 중간 | 높음 | **P2** | 비용 2배. 브랜치 빌드 구현 후 확장 |
| 스냅샷 포크 | 높음 | 높음 | **P2** | 충분한 프로젝트 축적 후 가치 발현 |

## YHAI 고유 포지셔닝

```
경쟁사 (v0, Bolt, Lovable):
  "프롬프트 입력 --> [블랙박스] --> 결과물"

YHAI:
  "전문가 대화 --> 요구사항 확정 --> [투명한 AI 팀 빌드] --> 결과물"
       |                |                    |
  전문가 디베이트     사용자 승인         코파일럿 개입
  다중 관점 제시     비용 예측           사고 과정 공개
                                        브랜치 선택
```

**YHAI의 핵심 메시지: "AI가 대신 만드는 것이 아니라, 사용자가 AI 팀과 함께 만드는 것."**
