# AI 웹사이트 자동 빌드 플랫폼 (YHAI) - 마스터 플랜

## Context

사용자가 Claude AI와 대화(티키타카)하며 원하는 서비스를 설명하면, 요구사항을 자동 정리하고, AI 에이전트 팀을 자동 생성하여 **풀스택 코드 + 자동 배포**까지 수행하는 포탈 플랫폼.

**접근 방식**: 기획 우선 — 서비스 시나리오 → 설계 → 디자인을 완료한 후 구현 시작.

현재 상태: Next.js 15.5.3 프론트엔드가 `frontend/`에 있고, `backend/`은 비어있음.

---

## 기술 스택 (확정)

| 영역 | 기술 |
|------|------|
| **Frontend** | Next.js 15.5.3 + React 19 + TailwindCSS v4 + shadcn/ui |
| **Backend** | NestJS + TypeScript |
| **DB** | PostgreSQL + Prisma ORM |
| **큐** | BullMQ + Redis |
| **AI** | Anthropic SDK (채팅) + Claude Agent SDK (오케스트레이션) |
| **실시간** | SSE (채팅 스트리밍) + WebSocket/Socket.IO (빌드 진행상황) |
| **공유 타입** | `packages/shared` (npm workspaces 모노레포) |
| **배포** | Docker + Vercel(프론트) + Railway/Fly.io(백엔드) |

## 전체 서비스 흐름

```
사용자 → [채팅 UI] → 대화 시작
                          ↓
              [도메인 전문가 자동 감지 + 초빙]
              - 대화 내용 분석 → 적합한 전문가 추천
              - 사용자가 수락/거부/변경 가능
              - 복수 전문가 동시 참여 (멀티 에이전트 채팅)
                          ↓
              [전문가와 티키타카 대화]
              - 각 전문가가 자기 영역에서 질문/조언
              - 사용자가 추가 전문가 직접 초빙 가능
                          ↓
                  [요구사항 자동 추출]
                          ↓
              사용자 확인/수정 → 확정
                          ↓
              [AI 개발팀 자동 생성] (PM Agent)
              - 역할 배정 (프론트/백/디자인/DB/DevOps)
              - 태스크 분해 & 의존성 그래프
                          ↓
              [에이전트 실행] (병렬, BullMQ)
              - 각 에이전트가 코드/설계 생성
                          ↓
              [결과물 조립] → 미리보기 → 자동 배포
```

## 도메인 전문가 시스템 (Expert Advisor System)

> 채팅 단계에서 사용자의 목적에 맞는 전문가를 자동 초빙하여 함께 대화하는 시스템

### 핵심 개념

**전문가 = 특화된 시스템 프롬프트를 가진 AI 페르소나**

사용자가 "쇼핑몰을 만들고 싶어"라고 하면, 시스템이 자동으로 **이커머스 전문가**와 **UI/UX 전문가**를 추천하고, 사용자가 수락하면 해당 전문가들이 대화에 참여합니다.

### 전문가 참여 방식

```
[자동 감지] 사용자 메시지 분석 → 도메인 키워드 매칭 + Claude 분류
     ↓
[추천 카드 UI] "이 대화에 다음 전문가를 추천합니다"
     - ✅ 이커머스 전문가 (수락)
     - ✅ UI/UX 전문가 (수락)
     - ❌ 결제 전문가 (거부 — 나중에 추가 가능)
     ↓
[멀티 전문가 채팅] 각 전문가가 자기 영역에서 발언
     - 전문가별 아바타/이름/색상으로 구분
     - 사용자는 언제든 + 버튼으로 추가 전문가 초빙
     - 불필요한 전문가는 퇴장 가능
```

### 전문가 카테고리 (예시)

| 도메인 | 전문가 | 역할 | 트리거 키워드 |
|--------|--------|------|---------------|
| **이커머스** | 서비스 판매 전문가 | 상품 구조, 결제 흐름, 재고 관리 설계 | 쇼핑몰, 판매, 상품, 결제 |
| **마케팅** | 광고/마케팅 전문가 | 랜딩페이지, CTA, 전환율 최적화 | 광고, 홍보, 마케팅, 랜딩 |
| **콘텐츠** | 콘텐츠 전략가 | 블로그, CMS, SEO 구조 설계 | 블로그, 콘텐츠, 미디어 |
| **SaaS** | SaaS 비즈니스 전문가 | 구독 모델, 요금제, 온보딩 설계 | 구독, SaaS, 요금제, 플랜 |
| **커뮤니티** | 커뮤니티 설계 전문가 | 회원 시스템, 게시판, 알림 구조 | 커뮤니티, 포럼, 게시판 |
| **예약/서비스** | 예약 시스템 전문가 | 예약 흐름, 일정 관리, 알림 | 예약, 스케줄, 일정 |
| **공통** | UI/UX 전문가 | 사용성, 디자인 패턴, 반응형 | (항상 참여 가능) |
| **공통** | 기술 아키텍트 | 기술 스택, 확장성, 성능 | (항상 참여 가능) |

### 기술 설계

- **전문가 레지스트리**: 각 전문가의 시스템 프롬프트, 아바타, 트리거 조건을 DB에 관리
- **도메인 감지기**: 사용자 메시지 → Claude 분류 API (가벼운 Haiku 호출) → 전문가 추천 목록
- **멀티 에이전트 채팅**: 하나의 대화에 복수 시스템 프롬프트를 조합하여 Claude에 전달
  - 방식 A: 단일 Claude 호출에 모든 전문가 페르소나 포함 (비용 효율)
  - 방식 B: 전문가별 개별 Claude 호출 → 응답 병합 (독립성 높음)
- **전문가 관리 UI**: 사이드 패널에 현재 참여 전문가 목록 + 추가/제거 버튼

### DB 모델 추가

```
ExpertProfile (id, name, domain, avatar, systemPrompt, triggerKeywords:jsonb, isDefault)
ConversationExpert (id, conversationId, expertId, joinedAt, leftAt?)
```

## 기획 팀 운영 체계

> 마스터 플랜을 개선하고 서비스를 기획하는 팀. 제한된 컨텍스트 안에서 정확한 의사결정을 보장하는 구조.

### 팀장 (Team Leader) — 서비스 기획 총괄

**1차 목적**: YHAI 서비스 기획 전반을 총괄하고, 팀원의 산출물을 통합하여 최종 기획 문서를 완성한다.

**핵심 원칙: Gate Review (관문 승인) 방식**
- 각 단계 완료 시 반드시 사용자 확인을 받은 후 다음 단계로 진행
- 사용자 미확인 상태에서는 절대 다음 단계로 넘어가지 않음

**작업 흐름:**
```
[팀장] 작업 지시 → [웹 검색 전문가] 조사
         ↓
[팀장] 조사 결과 검토 + 요약 → Slack 알림 (중간 보고)
         ↓
[사용자] 확인 ✅ → 다음 단계 진행
         ↓
[팀장] 작업 지시 → [서비스 플랜 전문가] 개선안 생성
         ↓
[팀장] 개선안 통합 + 기획 문서 작성 → Email 전송 (장문 기획)
         ↓
[사용자] 확인 ✅ → 플랜 반영 + 다음 Plan 단계 진행
```

**커뮤니케이션 채널:**

| 유형 | 채널 | 용도 | 예시 |
|------|------|------|------|
| 중간 보고 | **Slack** | 진행 상황, 간단한 결과 요약, 확인 요청 | "웹 조사 완료. 경쟁사 5개 분석 완료. 확인 부탁드립니다." |
| 장문 기획 | **Email** | 완성된 기획 문서, 상세 분석 리포트 | 서비스 시나리오 전문, 경쟁사 비교 분석표 |
| 긴급/질문 | **Slack** | 의사결정이 필요한 질문, 블로커 보고 | "A안과 B안 중 어느 방향으로 진행할까요?" |

**컨텍스트 관리 전략 (실수 방지):**

1. **파일 기반 상태 관리**: 모든 중간 산출물을 `docs/planning/` 에 md 파일로 저장
   - 컨텍스트 윈도우에 의존하지 않고, 파일을 읽어서 이전 상태 복원
2. **단계별 체크포인트**: 각 Gate Review 통과 시 진행 상태를 `docs/planning/progress.md`에 기록
3. **산출물 체인**: 각 팀원의 산출물이 다음 팀원의 입력이 됨 (명확한 의존성)
   - 웹 조사 리포트 → 서비스 플랜 전문가의 입력
   - 서비스 개선안 → 팀장의 통합 기획 문서 입력
4. **요약 우선**: 팀원 산출물을 팀장이 핵심만 요약하여 다음 팀원에게 전달 (컨텍스트 절약)
5. **결정 로그**: 주요 의사결정과 근거를 `docs/planning/decisions.md`에 누적 기록

**팀장이 관리하는 파일:**
- `docs/planning/progress.md` — 현재 진행 상태 + Gate Review 기록
- `docs/planning/decisions.md` — 의사결정 로그
- `docs/planning/master-plan.md` — 최종 통합 플랜

### 웹 검색 전문가 (Web Research Expert)

- **역할**: 기술 동향, 유사 서비스 조사, 현재 시스템과 비교 분석
- **조사 범위**: AI 웹빌더 (v0.dev, Bolt.new, Lovable, Create.xyz 등), 에이전트 오케스트레이션, 멀티 에이전트 채팅
- **산출물**: `docs/planning/research/` 폴더에 조사 리포트 저장

### 서비스 플랜 전문가 (Service Plan Expert)

- **역할**: 웹 검색 전문가의 분석을 토대로 창의적 서비스 개선안 생성
- **초점**: 차별화 포인트, UX 혁신, 비즈니스 모델, 기존 플랜 보완
- **산출물**: `docs/planning/proposals/` 폴더에 개선 제안서 저장

- `.mcp.json`에 Slack MCP 서버 설정 추가

### Plan 1: 서비스 시나리오 정의
> 사용자 여정을 구체적으로 설계

- [ ] **사용자 페르소나** 정의 (타겟 사용자는 누구인가?)
- [ ] **핵심 사용자 시나리오** 작성
  - 시나리오 1: 신규 사용자 → 회원가입 → 프로젝트 생성 → **전문가 자동 추천** → 대화 → 요구사항 확정

## 에이전트 오케스트레이션 (개념)

| 계층 | 역할 | 설명 | 단계 |
|------|------|------|------|
| L0 | Domain Expert Advisors | 도메인 전문가 — 사용자와 대화하며 요구사항 유도 | 채팅 단계 |
| L1 | PM Agent | 요구사항 → 팀 구성 + 태스크 분해 | 빌드 준비 |
| L2 | Specialist Agents | 역할별 코드/설계 생성 | 빌드 실행 |

**L0 전문가 역할:** 이커머스, 마케팅, 콘텐츠, SaaS, 커뮤니티, 예약, UI/UX, 기술 아키텍트 등
**L2 개발자 역할:** UI/UX 디자이너, 프론트엔드 개발자, 백엔드 개발자, DB 아키텍트, DevOps 엔지니어
