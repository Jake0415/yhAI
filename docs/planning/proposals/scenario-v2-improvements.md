## 1. 시나리오 3 전면 재설계: "AI 팀 자동 생성 -> 단계적 구현"

### 1.1 현재 시나리오 3의 문제점

기존 시나리오 3은 다음과 같은 한계가 있다.

| 문제 | 설명 |
|------|------|
| 고정 팀 구성 | 항상 UI/UX, 프론트엔드, 백엔드, DB, DevOps 5명이 생성됨. 프로젝트 특성과 무관한 획일적 팀 |
| 팀 생성 과정 불투명 | "팀을 구성하고 있습니다..." 한 줄로 끝남. PM의 판단 근거가 사용자에게 보이지 않음 |
| 단계적 구현 부재 | Phase 분해와 의존성 해결 과정이 없이 모든 에이전트가 동시에 시작하는 것처럼 표현 |
| 파일 충돌 대책 미정의 | 에이전트 간 동일 파일 충돌 방지 메커니즘이 시나리오에 반영되지 않음 |
| 사용자 개입 지점 부족 | 빌드 시작 후 사용자가 개입할 수 있는 체크포인트가 없음 |

### 1.2 재설계: PM Agent의 팀 동적 생성 과정

PM Agent가 요구사항을 분석하여 필요한 역할을 판단하는 과정을 사용자에게 투명하게 보여준다.

```

[PM Agent 분석 시작] -- 사용자에게 사고 과정 스트리밍
       |
       |  PM Agent의 분석 스트리밍:
       |  "요구사항을 분석하고 있습니다..."
       |
       |  1. 도메인 분석:
       |     - 이커머스(구독형) --> 결제 로직 필수
       |     - 회원 시스템 --> 인증/인가 필수
       |     - 배송 추적 --> 외부 API 연동 필요
       |

       |     - 프론트엔드: Next.js + React (SPA + SSR)

       |     - 이 프로젝트는 구독 결제와 배송 추적이 핵심입니다.
       |     - 별도 디자인 시스템은 불필요합니다 (shadcn/ui 기본 사용).
       |     - DevOps는 기본 템플릿으로 충분합니다.
       |
       v
[맞춤 팀 구성 제안] -- 사용자 확인 대기
       |
       |  +-----------------------------------------------+
       |  | PM Agent의 팀 구성 제안                         |
       |  |                                               |
       |  | "이 프로젝트에는 다음 4명의 팀이 적합합니다:"       |
       |  |                                               |
       |  | [v] Frontend 개발자                             |
       |  |     "구독 플랜 선택, 박스 커스터마이징 UI 구현"     |
       |  |                                               |
       |  | [v] Backend 개발자                              |
       |  |     "결제 API, 구독 관리, 회원 인증 구현"          |

       |  |                                               |

       |  |     "결제 흐름 E2E 테스트, 엣지 케이스 검증"       |
       |  |                                               |
       |  | [ ] + 역할 추가  [ ] 역할 제거                    |
       |  |                                               |
       |  | "DevOps는 기본 배포 템플릿을 사용하므로 별도       |
       |  |  에이전트 없이 PM이 직접 처리합니다."              |
       |  |                                               |
       |  | [팀 구성 승인] [수정하기]                         |
       |  +-----------------------------------------------+
       |
       v (사용자 승인)
       |
[태스크 분해 + Phase 설계]
```

핵심 차별점:
- **프로젝트별 맞춤 팀**: 간단한 랜딩 페이지라면 Frontend 1명만, 복잡한 SaaS라면 6~7명까지 동적 구성
- **PM의 판단 근거 공개**: 왜 이 역할이 필요하고 왜 저 역할은 불필요한지 사용자에게 설명
- **사용자 편집 가능**: 팀 구성을 사용자가 수정할 수 있음 (역할 추가/제거)

## 2. 6대 문제-해결 메커니즘

### 2.1 파일 충돌

**문제 설명**: 멀티 에이전트가 동일 저장소에서 동시 작업 시, 같은 파일을 서로 다른 방향으로 수정하여 코드가 깨진다.

**발생 시나리오**: Frontend Agent가 `src/types/api.ts`에 `ProductResponse` 타입을 정의하는 동시에, Backend Agent가 같은 파일에 `OrderResponse` 타입을 추가한다. 두 에이전트 모두 파일 끝에 내용을 추가하여 머지 시 한쪽 변경이 유실된다.

**YHAI 해결 메커니즘**:

```
[사전 예방] Git Worktree 격리
  - 각 에이전트에 독립 워크트리 부여
  - worktree-fe/, worktree-be/ 각각 독립된 HEAD와 index
  - 작업 중 다른 에이전트의 파일과 물리적으로 분리

[충돌 감지] 머지 전 사전 체크
  - PM Agent가 각 에이전트의 변경 파일 목록을 실시간 추적
  - 동일 파일 수정 감지 시 경고:
    "Frontend와 Backend가 모두 src/types/api.ts를 수정했습니다"

[자동 해결] 3-way 머지 시도
  - git merge --no-commit 으로 자동 머지 시도
  - 충돌 없음 --> 자동 커밋
  - 충돌 발생 --> PM Agent가 충돌 내용 분석 후 자동 해결 시도

[사용자 선택] 자동 해결 실패 시
  +------------------------------------------------+
  | 파일 충돌 발생: src/types/api.ts                  |
  |                                                  |
  | Frontend 버전:               Backend 버전:        |
  | export type ProductResponse  export type OrderRes |
  | = { id, name, price }       = { id, total }      |
  |                                                  |
  | [두 변경 모두 유지] [Frontend 우선] [Backend 우선]  |
  +------------------------------------------------+
```

### 2.2 컨텍스트 유실

**문제 설명**: 에이전트가 독립 컨텍스트 창에서 실행되므로, 다른 에이전트의 결정사항을 모른 채 작업하여 일관성이 깨진다.

**발생 시나리오**: DB 설계자가 `subscription` 테이블의 `status` 필드를 `ENUM('active', 'paused', 'cancelled')`로 정의했는데, Frontend Agent가 이를 모르고 `status: string`으로 구현하여 타입 불일치 발생.

**YHAI 해결 메커니즘**:

```
[공유 태스크 리스트] -- 중앙 단일 진실 공급원
  - 모든 에이전트가 읽고 쓸 수 있는 태스크 큐
  - 각 태스크에 결과물(아티팩트)이 첨부됨
  - 예: "DB 스키마 완료" 태스크에 Prisma 모델 파일 경로 첨부

[요구사항 대시보드 참조]
  - 모든 에이전트가 빌드 시작 시 동일한 요구사항 문서를 수신
  - 요구사항 문서에 데이터 모델, API 인터페이스 명세 포함
  - PM Agent가 Phase 1 완료 후 생성된 스키마를 요구사항 문서에 추가

[메시지박스 기반 합의]
  - 에이전트 간 인터페이스 결정 시 메시지박스로 직접 통신
  - 예: Backend --> Frontend: "Subscription.status는
    'active' | 'paused' | 'cancelled' ENUM입니다"
  - Frontend: "확인. SubscriptionBadge 컴포넌트에서 해당
    상태별 색상을 매핑합니다"

[Phase 경계 동기화]
  - Phase 1(DB) 완료 --> 결과물을 Phase 2 에이전트에 주입
  - 에이전트가 이전 Phase 결과를 참조하고 시작하므로
    컨텍스트 단절 구조적 방지
```

### 2.3 에러 전파

**문제 설명**: 한 에이전트의 잘못된 출력이 다음 에이전트의 입력이 되어, 파이프라인 전체에 걸쳐 잘못된 결과를 생산한다.

**발생 시나리오**: DB 설계자가 `price` 필드를 `Float`로 정의했는데, Backend에서 정수 연산을 수행하여 68.81원이 0.6878원으로 변환되고, Frontend에서 이를 그대로 표시.

**YHAI 해결 메커니즘**:

```
[체크포인트 시스템]
  - 매 Phase 완료 시 전체 상태 스냅샷 저장
  - Phase 2에서 문제 발견 시 Phase 1부터 재실행 가능
  - 재실행 범위를 문제 발생 Phase로 한정

[QA 에이전트 검증 게이트]
  - Phase 4에서 QA 에이전트가 통합 테스트 실행
  - 타입 불일치, 데이터 변환 오류 등을 자동 감지
  - 실패 시 해당 에이전트에게 수정 지시 + 재테스트

[롤백 메커니즘]
  - 사용자가 "이전 Phase로 돌아가기" 선택 가능
  - Git 커밋 히스토리 기반으로 특정 Phase 시점으로 복원
  - 에이전트에게 수정된 지시와 함께 재실행

[에이전트 재시작]
  - 에이전트가 3회 이상 동일 에러 반복 시 자동 재시작
  - 재시작 시 깨끗한 컨텍스트 + 이전 시도의 실패 로그를 참조
  - PM Agent가 대안 접근법을 지시
```

### 2.4 무한 루프

**문제 설명**: 에이전트가 종료 조건을 인식하지 못하고 동일한 작업을 반복하거나, 에러 수정 시도가 새로운 에러를 만들어 무한히 순환한다.

**발생 시나리오**: Frontend Agent가 CSS 레이아웃 버그를 수정하는데, 수정할 때마다 다른 컴포넌트의 레이아웃이 깨져서 끊임없이 수정-확인-수정을 반복. 30분간 동일 파일을 계속 수정.

**YHAI 해결 메커니즘**:

```
[가드레일 1: max_steps 캡]
  - 에이전트당 최대 실행 스텝 수 설정 (기본: 30 steps)
  - 상한 도달 시 에이전트 자동 중단
  - PM Agent에게 "Frontend Agent가 30 steps를 소진했습니다" 보고

[가드레일 2: 반복 출력 감지]
  - 에이전트의 최근 N개 출력을 비교
  - 동일하거나 유사한 출력이 3회 이상 반복되면 Loop Drift로 판정
  - 즉시 중단 + 사용자 알림:
    "Frontend Agent가 같은 파일을 반복 수정하고 있습니다.
     [에이전트 재시작] [직접 수정 지시] [이 작업 건너뛰기]"

[가드레일 3: 시맨틱 완료 체크]
  - 에이전트 출력이 태스크 목표를 실제로 달성했는지 검증
  - PM Agent가 각 태스크의 완료 조건을 사전 정의
  - 예: "SubscriptionPlanPage 컴포넌트가 존재하고,
    props로 plans 배열을 받고, 가격을 표시한다"
  - 조건 미충족 시 구체적 피드백과 함께 재시도 (최대 3회)

[사용자 알림 UX]
  +------------------------------------------------+
  | [!] Frontend Agent 이상 감지                     |
  |                                                  |
  | SubPlanPage.tsx를 5회 연속 수정 중입니다.          |
  | 마지막 3회 변경이 거의 동일합니다.                  |
  |                                                  |
  | [에이전트 재시작]                                  |
  | [직접 지시 입력] "가격 테이블은 grid로 구현해주세요" |
  | [이 태스크 건너뛰기]                               |
  | [전체 빌드 중단]                                   |
  +------------------------------------------------+
```

### 2.5 비용 폭발

**문제 설명**: 에이전트 실행에는 LLM API 비용이 발생하며, 멀티 에이전트 병렬 실행 시 비용이 기하급수적으로 증가할 수 있다. 특히 무한 루프나 과도한 디버깅 시 예측 불가능한 비용이 발생한다.

**발생 시나리오**: 3개 에이전트가 병렬 실행 중 1개가 무한 루프에 빠지고, 나머지 2개도 충돌 해결을 위해 반복 호출. 2시간 동안 $15-40 소진. 사용자는 빌드 완료 후에야 비용을 인지.

**YHAI 해결 메커니즘**:

```
[토큰 예산 카운터]
  - 프로젝트별 토큰 예산 사전 설정
  - 모든 API 호출 시 카운터 증가
  - 예산 70% 소진 시 경고, 90% 소진 시 사용자 승인 요청

[실시간 비용 대시보드]
  - Mission Control에 현재 비용 실시간 표시
  - "현재 비용: $1.20 / 예산 $5.00"
  - 에이전트별 비용 분배 표시:
    Frontend: $0.45 | Backend: $0.50 | DB: $0.15 | PM: $0.10

[사용자 승인 게이트]
  - 예산 초과 시 자동 일시정지:
    +------------------------------------------------+
    | [!] 토큰 예산 90% 도달                           |
    |                                                  |
    | 현재 비용: $4.50 / 예산 $5.00                     |
    | 남은 작업: Phase 3 (결제 연동), Phase 4 (QA)       |
    | 예상 추가 비용: ~$1.50                            |
    |                                                  |
    | [예산 $2.00 추가] [현재 상태로 완료] [빌드 취소]    |
    +------------------------------------------------+

[빌드 전 비용 예측]
  - Phase 실행 계획 단계에서 예상 비용을 사전 표시
  - "총 예상 비용: ~$2.50 (Phase 4개, 에이전트 4명)"
  - 사용자가 비용을 확인하고 빌드 시작 결정
```

### 2.6 품질 불일치

**문제 설명**: 각 에이전트가 독립적으로 코드를 생성하므로, 코딩 스타일, 네이밍 컨벤션, 에러 처리 방식 등이 에이전트마다 달라 전체 코드베이스의 일관성이 깨진다.

**발생 시나리오**: Frontend Agent는 camelCase를 사용하고 Backend Agent는 snake_case를 사용. Frontend는 try-catch로 에러를 처리하고 Backend는 에러를 무시. 결과적으로 하나의 프로젝트인데 두 사람이 따로 만든 것처럼 보임.

**YHAI 해결 메커니즘**:

```
[공유 코딩 컨벤션 문서]
  - PM Agent가 빌드 시작 시 프로젝트 코딩 컨벤션 생성
  - 모든 에이전트의 시스템 프롬프트에 포함:
    - 네이밍: camelCase (변수/함수), PascalCase (컴포넌트/타입)
    - 에러 처리: 모든 API 호출에 try-catch + 사용자 친화적 에러 메시지
    - 파일 구조: feature-based 폴더 구조
    - 임포트 순서: 외부 라이브러리 > 내부 모듈 > 상대 경로

[PM Agent 코드 리뷰]
  - 각 에이전트의 커밋을 PM Agent가 자동 리뷰
  - 컨벤션 위반 감지 시 에이전트에게 수정 요청
  - 리뷰 결과를 사용자에게 요약 보고:
    "Frontend Agent의 ProductCard에서 에러 처리 누락을 발견하여
     수정을 요청했습니다. 수정 완료."

[린트/포맷 자동 실행]
  - 모든 에이전트 커밋 전 ESLint + Prettier 자동 실행
  - 통과하지 못한 커밋은 거부
  - 에이전트가 린트 에러를 보고 자동 수정
```

## 3. 창의적 추가 아이디어 (7개)

### 3.1 코파일럿 빌드 (Copilot Build)

**설명**: 빌드 진행 중 사용자가 실시간으로 개입하여 방향을 수정할 수 있다. 기존 AI 빌더는 "프롬프트 입력 --> 결과 대기"의 일방향 구조지만, YHAI에서는 빌드 중에도 사용자가 채팅으로 지시를 보낼 수 있다.

```
[Mission Control 하단 입력창]

사용자: "구독 플랜 페이지에 연간 할인 옵션도 추가해주세요"
  |
  v
PM Agent: "확인. Frontend Agent에 태스크를 추가합니다.
  현재 Phase 2 진행 중이므로 바로 반영됩니다."
  |
  v
Frontend Agent: 실행 중인 태스크에 연간 할인 옵션 추가
```

- **사용자 가치**: 빌드 결과를 기다린 후 수정하는 것이 아니라, 진행 중에 방향을 조정하여 재빌드 비용 절감
- **구현 복잡도**: 중간 -- PM Agent의 태스크 큐에 실시간 추가 기능 필요
- **차별성**: v0, Bolt, Lovable 모두 "입력 --> 대기 --> 결과" 구조. 빌드 중 개입은 없음

### 3.2 사고 과정 스트리밍 (Thinking Stream)

**설명**: 에이전트의 의사결정 과정을 사용자에게 투명하게 보여준다. 왜 이 라이브러리를 선택했는지, 왜 이 구조로 설계했는지, 어떤 대안을 고려했고 왜 기각했는지를 실시간으로 스트리밍한다.

```
[에이전트 사고 과정 패널] -- 접기/펼치기 가능

Backend Agent 사고 과정:
  "결제 연동 방식을 결정합니다..."

  고려한 옵션:
  1. 토스페이먼츠 직접 연동
     + 국내 점유율 1위, 문서 우수
     - 정기결제 설정이 복잡
  2. Bootpay 정기결제 API   <-- 선택
     + 구독 결제 전용 API, 설정 간단
     + 카카오페이 + 카드 결제 통합 지원
     - 수수료 약간 높음
  3. Stripe
     - 한국 원화 결제 제약

  결정: Bootpay 정기결제 API (요구사항의 카카오페이 + 카드 결제
  동시 지원 조건에 가장 부합)
```

- **사용자 가치**: 블랙박스 불안감 해소. 개발자 사용자는 에이전트의 기술 결정을 학습할 수 있고, 비개발자도 왜 이렇게 만들어졌는지 이해 가능
- **구현 복잡도**: 낮음 -- Claude의 extended thinking 기능을 파싱하여 UI에 표시
- **차별성**: 모든 경쟁사가 블랙박스. 사고 과정을 보여주는 AI 빌더는 없음

### 3.3 브랜치 빌드 (Branch Build)

**설명**: 빌드 중 문제가 발생하거나 여러 해결 방안이 있을 때, 에이전트가 Git 브랜치를 분기하여 각 방안을 별도로 구현한다. 사용자가 결과를 비교하고 원하는 브랜치를 선택한다.

```
Backend Agent: "인증 방식에 대해 2가지 접근이 가능합니다."

  +-- Branch A: JWT + httpOnly Cookie --------+
  | + 서버리스 친화적, 세션 서버 불필요          |
  | - 토큰 갱신 로직 필요                       |
  | [미리보기]                                 |
  +-------------------------------------------+

  +-- Branch B: Session 기반 인증 ---------------+
  | + 구현 단순, 즉시 만료 가능                    |
  | - Redis 세션 스토어 필요                      |
  | [미리보기]                                    |
  +----------------------------------------------+

  [Branch A 선택] [Branch B 선택]
```

- **사용자 가치**: 기술 결정에서 사용자에게 선택권 부여. "AI가 결정한 것"이 아니라 "사용자가 선택한 것"이 되어 결과물에 대한 주인의식 증가
- **구현 복잡도**: 중간 -- Git 브랜치 분기 + 각 브랜치별 에이전트 실행 + 비교 UI
- **차별성**: 경쟁사는 하나의 결과만 생성. 분기 선택은 YHAI 고유 경험

### 3.4 A/B 빌드 (A/B Build)

**설명**: 동일한 요구사항을 서로 다른 디자인/아키텍처 접근으로 병렬 생성한다. 사용자가 두 결과물을 나란히 비교하고 선호하는 버전을 선택하거나 두 버전의 장점을 조합한다.

```
[A/B 빌드 모드 선택]

사용자: "랜딩 페이지를 두 가지 스타일로 만들어주세요"

  +-- Version A -------------------+  +-- Version B -------------------+
  | 미니멀 스타일                    |  | 임팩트 스타일                    |
  |                                |  |                                |
  | +----------------------------+ |  | +----------------------------+ |
  | | [깔끔한 타이포그래피]        | |  | | [대형 히어로 이미지]         | |
  | | [여백 중심 레이아웃]         | |  | | [동영상 배경]               | |
  | | [단색 CTA 버튼]             | |  | | [그라데이션 CTA 버튼]        | |
  | +----------------------------+ |  | +----------------------------+ |
  |                                |  |                                |
  | 전환율 예상: 3.2%               |  | 전환율 예상: 4.1%               |
  | 로딩 속도: 1.2s                 |  | 로딩 속도: 2.8s                 |
  +--------------------------------+  +--------------------------------+

  [A 선택] [B 선택] [A의 레이아웃 + B의 CTA 버튼 조합]
```

- **사용자 가치**: 디자인 결정에서 비교 선택이 가능. 특히 비개발자에게 "보고 선택"하는 직관적 경험 제공
- **구현 복잡도**: 높음 -- 동일 요구사항으로 2개의 독립 빌드를 병렬 실행 + 비교 UI + 조합 기능
- **차별성**: 경쟁사는 하나의 결과만 생성. A/B 비교는 디자인 에이전시 수준의 경험

### 3.5 전문가 디베이트 (Expert Debate)

**설명**: 시나리오 1-2의 전문가 대화 단계에서, 전문가들이 서로 다른 의견을 가질 때 토론하는 과정을 사용자에게 보여준다. 사용자는 토론을 관찰하고 최종 결정을 내린다.

```
[전문가 디베이트 발생]

  SaaS 전문가: "구독 플랜은 3단계(Free/Pro/Enterprise)가
    업계 표준입니다. 전환율 최적화에 검증된 구조입니다."

  UX 전문가: "반대합니다. 반려동물 구독은 B2C 서비스이므로
    3단계 플랜은 복잡합니다. 단일 플랜 + 주기 선택이
    사용자 혼란을 줄입니다."

  SaaS 전문가: "단일 플랜은 업셀 기회를 놓칩니다.
    최소 2단계(Basic/Premium)를 권장합니다."

  UX 전문가: "그렇다면 2단계 + 주기 선택(월간/연간)으로
    타협하면 어떨까요?"

  +------------------------------------------------+
  | 당신의 선택:                                     |
  | [A] 3단계 플랜 (Free/Pro/Enterprise)             |
  | [B] 2단계 + 주기 선택 (Basic/Premium x 월간/연간)  |
  | [C] 단일 플랜 + 주기 선택                         |
  | [D] 직접 입력                                    |
  +------------------------------------------------+
```

- **사용자 가치**: 전문가의 다양한 관점을 이해하고 정보에 기반한 결정을 내릴 수 있음. 단순히 AI 추천을 따르는 것이 아닌 "사용자의 의사결정"이 됨
- **구현 복잡도**: 낮음 -- 전문가 페르소나 간 의견 충돌 시 토론 형식으로 출력하도록 프롬프트 설계
- **차별성**: 모든 경쟁사가 단일 관점 제시. 다중 관점 토론은 YHAI 고유 경험

### 3.6 빌드 리플레이 (Build Replay)

**설명**: 완성된 앱의 생성 과정을 타임랩스 영상처럼 재생할 수 있다. 빈 프로젝트에서 완성된 앱까지 코드가 한 줄씩 추가되고 화면이 구성되는 과정을 가속 재생으로 보여준다.

```
[빌드 완료 후]

  "빌드 과정을 리플레이로 보시겠어요?"

  +------------------------------------------------+
  | [빌드 리플레이]                        [x1] [x4] |
  |                                                  |
  |  00:00  빈 프로젝트 생성                          |
  |  00:15  DB 스키마 정의 (6개 테이블)                |
  |  00:30  Backend API 뼈대 생성                     |
  |  00:45  Frontend 레이아웃 + 라우팅                 |
  |  01:00  ProductCard 컴포넌트 구현                  |
  |  01:15  [지금 보는 중] SubscriptionPlan 페이지     |
  |  ...                                             |
  |  03:00  E2E 테스트 통과                           |
  |                                                  |
  |  좌측: 파일 트리 변화    우측: 라이브 프리뷰 변화     |
  |                                                  |
  |  [<<] [>] [>>]          타임라인 슬라이더           |
  +------------------------------------------------+
```

- **사용자 가치**: 교육적 가치(어떤 순서로 앱이 만들어지는지 학습), 공유 가치(SNS에 빌드 과정 공유 가능), 신뢰 구축(AI가 실제로 무엇을 했는지 확인)
- **구현 복잡도**: 중간 -- Git 커밋 히스토리 + 각 커밋 시점의 프리뷰 스냅샷을 타임라인 UI로 재생
- **차별성**: 경쟁사에 이런 기능 전무. 바이럴 마케팅 소재로 활용 가능

### 3.7 스냅샷 포크 (Snapshot Fork)

**설명**: 완성된 프로젝트를 다른 사용자가 "포크"하여 자신의 서비스로 커스터마이징할 수 있다. YHAI 사용자 커뮤니티에서 공개된 프로젝트를 탐색하고, 마음에 드는 프로젝트를 기반으로 시작한다.

```
[YHAI 갤러리]

  인기 프로젝트:
  +-------------------+  +-------------------+  +-------------------+
  | 펫박스 구독 서비스  |  | 카페 예약 시스템    |  | SaaS 대시보드      |
  |                   |  |                   |  |                   |
  | [스크린샷]         |  | [스크린샷]         |  | [스크린샷]         |
  |                   |  |                   |  |                   |
  | 구독 결제, 배송    |  | 예약, 메뉴 관리    |  | 분석, 팀 관리      |
  | 추적, 회원 관리    |  | POS 연동           |  | 결제, 대시보드      |
  |                   |  |                   |  |                   |
  | [포크하기]         |  | [포크하기]         |  | [포크하기]         |
  +-------------------+  +-------------------+  +-------------------+

  사용자가 "포크하기" 클릭:
    --> 프로젝트 복사 + 전문가 대화 시작
    --> "펫박스를 기반으로 어떤 부분을 바꾸고 싶으세요?"
    --> 사용자: "반려동물 대신 꽃 정기배송으로 바꾸고 싶어요"
    --> 전문가: 도메인 변경에 필요한 수정사항 분석 + 부분 재빌드
```

- **사용자 가치**: 처음부터 만들 필요 없이 검증된 구조에서 시작. 온보딩 시간 대폭 단축. 커뮤니티 효과로 플랫폼 가치 증가
- **구현 복잡도**: 높음 -- 프로젝트 공유 시스템, 갤러리 UI, 포크 + 부분 재빌드 엔진
- **차별성**: Lovable의 템플릿과 유사하지만, YHAI는 사용자가 만든 실제 프로젝트를 포크하고 전문가와 대화하며 커스터마이징하는 점이 다름

## 마스터 플랜 반영 사항

### 1. `master-plan.md` 수정이 필요한 영역

**에이전트 오케스트레이션 섹션 보강**:

현재 마스터 플랜의 "에이전트 오케스트레이션 (개념)" 섹션에 다음을 추가해야 한다.

```
| 계층 | 역할 | 설명 | 단계 |
|------|------|------|------|
| L1 | PM Agent | 요구사항 분석 -> 동적 팀 구성 -> Phase 분해 | 빌드 준비 |
                  (기존: "요구사항 -> 팀 구성 + 태스크 분해"를 확장)
```

PM Agent의 구체적 책임:
- 요구사항 분석하여 필요 역할 판단 (고정 5명이 아닌 동적 N명)
- Phase 분해 + 의존성 그래프 생성
- 에이전트별 Git Worktree 생성 및 관리
- 공유 태스크 리스트 관리
- 에이전트 간 충돌 감지 및 해결
- 코드 리뷰 + 컨벤션 준수 검증

**리스크 및 대응 섹션 교체**:

현재:
```
| 에이전트 파일 충돌 | 태스크 단위 잠금, 조립 시 감지 |
```

변경:
```
| 에이전트 파일 충돌 | Git Worktree 격리 + 자동 3-way 머지 + 사용자 선택 폴백 |
| 무한 루프/비용 폭발 | max_steps 캡 + 토큰 예산 + 반복 감지 + 사용자 승인 게이트 |
| 에러 전파 | Phase 경계 체크포인트 + QA 에이전트 검증 게이트 + 롤백 |
| 컨텍스트 유실 | 공유 태스크 리스트 + 메시지박스 + Phase 경계 동기화 |
| 품질 불일치 | 공유 코딩 컨벤션 + PM 코드 리뷰 + 자동 린트 |
```

### 2. `user-scenarios.md` 수정 범위

- **시나리오 3 전면 교체**: 본 제안서의 1.2~1.6 내용으로 교체
- **시나리오 1 보완**: 전문가 디베이트 기능 추가 (선택적)
- **시나리오 4 보완**: 코파일럿 빌드, 사고 과정 스트리밍 반영

### 3. 로드맵 반영

**Phase 4 (AI 팀 자동 생성 + 오케스트레이션)** 세부 항목 추가:

```
Phase 4: AI 팀 자동 생성 + 오케스트레이션
  - [ ] PM Agent: 요구사항 분석 -> 역할 판단 로직
  - [ ] PM Agent: Phase 분해 + 의존성 그래프 생성
  - [ ] Git Worktree 관리 모듈 (생성/삭제/머지)
  - [ ] 공유 태스크 리스트 (BullMQ + Redis)
  - [ ] 메시지박스 (에이전트 간 통신 채널)
  - [ ] 가드레일 인프라: max_steps, 토큰 예산, 반복 감지, 시맨틱 완료 체크
  - [ ] 실시간 비용 대시보드 (WebSocket)
  - [ ] Mission Control v2 UI (Phase별 진행, 에이전트별 상태, 사고 과정)
  - [ ] 코파일럿 빌드 입력창 (빌드 중 사용자 개입)
```

## YHAI 고유 포지셔닝 요약

```
경쟁사 (v0, Bolt, Lovable):
  "프롬프트 입력 --> [블랙박스] --> 결과물"

YHAI:
  "전문가 대화 --> 요구사항 확정 --> [투명한 AI 팀 빌드] --> 결과물"
       |                |                    |
  전문가 디베이트     사용자 승인         코파일럿 개입
  다중 관점 제시     비용 예측           사고 과정 공개
                                        브랜치 선택
```

YHAI의 핵심 메시지: **"AI가 대신 만드는 것이 아니라, 사용자가 AI 팀과 함께 만드는 것."**

경쟁사가 "자동화"에 집중할 때, YHAI는 "협업"에 집중한다. 이 차이가 Devin의 실패 원인(모호한 요구사항, 사용자 소외)을 구조적으로 해결하는 YHAI만의 강점이다.
